I Built an Agentic AI Project Manager for a Hackathon

April 27 2026 | 7 min read

A few weeks ago my team entered an Agentic AI Hackathon and we built SentinelPM — an autonomous project management system. The pitch was simple: project managers spend a huge chunk of their time on repetitive, mechanical tasks like chasing overdue tickets, updating risk registers, and sending the same status emails to clients over and over. What if an AI agent just handled all of that on its own?

We weren't trying to replace PMs. The goal was to get the tedious stuff off their plate so they could spend their time on the decisions that actually need a human — prioritization calls, client relationships, things that require judgment. That framing ended up shaping everything about how we designed the system.

Tech stack: n8n · Google Gemini · Jira Cloud · Google Sheets · Gmail API · Atlassian REST API

How It Works: Two Pipelines

We structured SentinelPM as two separate agentic pipelines, each with its own trigger and purpose. They share the same Jira and Gemini integrations but operate independently.

Pipeline 1 — Risk & Prioritization Agent

This one runs on a schedule. Every morning it wakes up, pulls live ticket data from Jira via the Atlassian REST API, and feeds that data into Google Gemini to identify risks — things like tickets that are overdue, blocked, or assigned to someone who already has a full plate.

Gemini's findings get appended to a Google Sheets risk register so there's always a running log. Then the agent composes a risk summary email and sends it directly to the PM. And here's the part I thought was the coolest: it automatically reassigns overdue tickets in Jira, pulling from a workload calculation to find whoever on the team has the most available capacity.

So by the time the PM opens their laptop in the morning, the risk register is already updated, their inbox has a summary, and the overdue tickets have already been redistributed.

Pipeline 2 — Client Communication Agent

This pipeline is event-driven rather than scheduled. It watches the PM's Gmail inbox, and when a client email comes in asking for a project update, it kicks off automatically.

The agent pulls current Jira ticket data, sends it to Gemini with the client's email as context, and Gemini drafts a response tailored to what the client actually asked. The agent then sends that reply automatically. The PM doesn't have to touch it unless they want to.

We also added PDF handling — if a client sends a report or brief as an attachment, the agent reads it, extracts the key insights, and surfaces a clean summary to the PM rather than making them dig through the whole document.

What Broke (And How We Fixed It)

Honestly, debugging this was where I learned the most. A few specific things that cost us a lot of time:

The n8n Jira node was built on a deprecated Atlassian endpoint. We kept getting authentication failures that made no sense until we realized the built-in node wasn't hitting the right API. We had to ditch it and swap to raw HTTP request nodes pointing directly at the new JQL search endpoint. Not fun to figure out mid-hackathon.

Jira's reassignment API does not accept display names or plain-text priority labels. It wants Account ID UUIDs for users and numeric IDs for priority levels — so "High" needs to be 2, and "Patrick Rapalo" needs to be a UUID like 5b10a2844c20165700ede21g. We spent a long time debugging 400 errors before realizing the API was rejecting our payloads for this reason. Once we figured it out and mapped the IDs correctly, the reassignment worked perfectly.

Gemini's output path in n8n is $json.output, not $json.text. That one sounds small but it broke our entire response pipeline until we caught it.

What I Took Away From This

This was the first time I built something that I would genuinely call agentic. Not a chatbot, not a model that answers questions — something that wakes up on its own, takes actions in real systems, and creates side effects in the world. Emails get sent. Tickets get reassigned. Spreadsheets get updated. All without a human clicking anything.

That shift from query/response to trigger/action/side-effect feels like a fundamentally different mode of building with AI. There's a lot more to think about — error handling, when the agent should pause and ask for confirmation, how to make its reasoning visible to the PM rather than a black box. We touched on some of this but there's a lot more to explore.

I want to keep building in this space. The idea of agents that run in the background and handle the operational overhead of knowledge work is something I think is genuinely useful, not just a demo.
